### Findings

The prior round used R10, so the new findings are numbered from R11.

**R11 (medium; developer; G2 and H1 exit rule, PRIME.4). A core system that is absent from `results.json` is skipped silently, and the run exits 0.**
- **Where.** tools/rehearsal_report.py:1220-1225. `all_systems` is taken from `results["systems"]`, and nothing compares it with `config/core_systems`.
- **Probe.** I deleted `systems/chua` from a complete world. The `config/core_systems` value is still `['lorenz63', 'rossler', 'chua']`. The run gives **exit 0**, 0 "not computable" items, and "governs 8 of 8 parts".
- **Why it matters.**
  - The module docstring (lines 108-116) says "0 iff every row is computed (the 18 criteria, V7, every H3a pair …)". The brief requires exit 0 only on a complete world.
  - Here 23 rows and one H3a block of a core system are missing, and nothing is counted. This defect predates this round, but it breaks the property that H1 now relies on: H1 makes exit 0 reachable, and exit 0 is the gate.
- **Fix.**
  - In `run`, for each `config/core_systems` entry that is absent from `results["systems"]`, record `rep.nc(f"system {s}", "in config core_systems but not in results.json")`.
  - When `--systems` restricts the set, check only the requested ones (that already happens at line 1224). The fix covers the unrestricted case.
  - Treat an absent or unreadable `core_systems` leaf as "not computable", with no default.
  - Add a unit test: delete one system from `write_run`, then expect exit 2 and one item.

**R12 (low; developer; H1 "not used for anything"). A dump with a defect still supplies information values.**
- **Where.**
  - `open_dump` records a MISMATCH for a `meta/system` or `meta/preset` that differs from the run's, then returns the view anyway (lines 883-888, 898).
  - `kappa_from_dump` refuses only the leaf that failed (lines 849-851). The same system's other three leaves still print a point kappa.
- **Probe.**
  - I set the Rössler dump's `meta/preset` to `"smoke"`. The run exits 1 with 1 MISMATCH, and the summary still reports "point kappa shown as information for 12", Rössler included.
  - In the H3c-off-by-1e-6 world, H2c and H2d of the same dump still give information values ("9 of 12").
- **Why it matters.**
  - H1 says "A dump that fails its reproduction check … is not used for anything". The brief requires the point kappa to come only from a reproducing dump.
  - Exit 1 already blocks the run, and the value never enters a projection. So the only harm is an information number printed into a record from a dump that is known not to belong to the run.
- **Fix.**
  - Mark the `DumpView` unusable on its first defect, whether a provenance mismatch or any failed `check_reproduction`. Refuse every later `kappa_from_dump` on it with `NotComputable` ("the dump of <system> failed a check; not used").
  - Then update the counts in the two tests (9 becomes 8 for one failing H3c leaf per system, if the H3c check runs last). Alternatively, have the planner rule that per-leaf use is what H1 means.

**R13 (low; developer; text). The summary hard-codes the range "[0.7071, 1]".**
- **Where.** tools/rehearsal_report.py:1157.
- **Why it matters.** The range is `kappa_range(E_run, E_full)`. That is [0.7071, 1] only for E 2 → 4. A smoke run (E 1) has [0.5, 1] (`kappa_range(1, 4) = (0.5, 1.0)`). The rows print the right range, but the summary line would state a false one in the record.
- **Fix.** Format the range from `kappa_range(int(cfg["n_eval_draws"]), full.n_eval_draws)`, or from the rows' own `f_lo/f_hi` ratio. Keep the test's string for the pilot world.
