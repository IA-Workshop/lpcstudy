## Findings

**R7 (medium; developer; PRIME.4, G2). An unrecognised `KAPPA_POLICY` value applies the range but counts nothing, so a FALLBACK run exits 0.**
- **Where.** tools/rehearsal_report.py:955-966 and 1174.
  - The "range governs" `rep.nc` is under `if KAPPA_POLICY == "range"`, and the point branch is under `== "point"`.
  - Any other value, for example `"Range"`, `"points"` or `None`, falls through both. It keeps the range factors and prints `(FALLBACK)` in the row, but it records no "not computable" item and suppresses the "exit 0 is unreachable" line.
- **Probed** (the test module's synthetic world, reproducing dumps): `"Range"`, `"points"` and `None` each give **exit 0**, with 0 "not computable" lines and 12 FALLBACK rows.
- **Why it matters.**
  - G2 counts every FALLBACK toward exit 2.
  - The constant is the documented place where the owner's choice (a) or (b) is to be written (docstring at line 164), so a typo at that moment is plausible.
  - The result would be a silent exit 0 on a run whose H2c, H2d and H3c projections are the fallback range. This is the uncounted fallback that PRIME.4 forbids.
- **Fix.**
  - Validate the value once, at the start of `run`, against `{"range", "point"}`. On any other value, raise (exit 2, "unknown KAPPA_POLICY").
  - Alternatively, restructure the branch so that every non-`"point"` path records the `rep.nc`.
  - Add a unit test: monkeypatch an unknown value, then expect exit 2, or the FALLBACK rows counted.
  - Optionally, record the policy in `rep.data` (`--json`), so the governing rule is in the machine-readable output and not only in the summary text.

**R8 (low; developer, with a wording note for the planner). A `None` H3a pair is always labelled "zero log-rank variance", but production also writes `None` for an empty regime.**
- **Where.**
  - tools/rehearsal_report.py:98 and 1112-1113 (report line);
  - 1257-1258 (the "not computable" reason);
  - analysis.py:1926-1928: `None` with reason "empty regime" when a regime of the pair has no test state; this is counted in `n_empty_regimes`, not in `n_degenerate_pairs`.
- **Why it matters.** The handling is correct in both cases: counted, "not determined". Only the stated reason can be false, and the report is a record that the owner reads for the sample-size decision. G1's text has the same narrow wording.
- **Fix.** Word it "p_raw None (empty regime or zero log-rank variance; see the run's H3a reason)", or read `H3a/reason` from the results (the fixtures would then need that leaf). This is a text change only.

**R9 (low; developer). A lower-bound pair prints `p_full <= 0`.**
- **Where.**
  - tools/rehearsal_report.py:506-508 and 1117-1118.
  - With chi2_full = 2 × 1373.87, `chi2.sf` underflows to 0.0, so the line reads `p_full <= 0` (probed: `p_full` 0.0 for `p_raw` 1e-301 and 0.0).
- **Why it matters.** The true projected p is positive, so "≤ 0" is a false inequality. The reading is unaffected, since 0 and the true value are both far below 0.01/m.
- **Fix.** For a lower-bound pair, print and store the valid bound `p_full < 1e-300`. It is valid because the factor is at least 1 and sf is decreasing. Alternatively print `sf(...)` with "(underflow)". The test's `p_full <= 1e-300` stays true.

**R10 (low; planner and owner; no code change unless ruled). G2 and working default (a) conflict, and the fate of the `"point"` branch.**
- **The conflict.** G2's exit-0 clause requires a point kappa_E from a reproducing dump. Default (a) makes the range govern. Applied literally together, exit 0 is unreachable for any pilot run. The developer applied both as written and raised this as open question 1, which is correct.
- **What the planner should do.**
  - Add a clause to G2 for (a): for example, under (a) the range is the rule, not a FALLBACK, and is not counted. Or else confirm that exit 2 is intended until (b).
  - Rule on open question 2. If (a) becomes final, remove the `"point"` branch, because the note says the present estimate is "never used in a projection". If (b) is chosen, it brings a different estimator (half-split κ̂ with its jackknife range), not this point estimate, so `"point"` should not be the switch for it.
