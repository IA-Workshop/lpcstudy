## Findings

**R1 (medium; acceptance a1; must be fixed before the a1 smoke runs).** The predicted added-leaf count in the Log is wrong.

- **Where:** `docs/agent/records/work/WU-0003-dev-rehearsal.md:273`, Pending step 3.
- **The claim:** the Log predicts 8 + 2 × (number of `estimators` entries) added leaves, on the premise that every trained estimator appears both in `estimators` and in `systems/<s>/validation/estimators`.
- **What the code does:**
  - `run_system` builds `validation/estimators` as a snapshot (`lpcstudy/experiments.py:503`, `{k: v for k, v in study.estimator_log.items() if system in k}`). The snapshot is taken after the core cell and before the noise sweep.
  - Estimators trained later appear only in the top-level `estimators`. At smoke (`noise_levels=(0.01, 0.02)`), that is the 0.02 network.
  - The DEV-0 smoke `s3default` confirms this: `estimators` has two keys (0.01 and 0.02), and `validation/estimators` has one (0.01).
  - So the expected count at smoke is 8 + N_top + N_val = 8 + 2 + 1 = **11**, not 12.
- **Why it matters:** a1 requires that "the added leaves are exactly this set, counted in the Log". A prediction that is corrected after the run would be a criterion adjusted after the fact (PRIME.2, VV.3).
- **Fix:** before the smokes run, restate the count in the Log as 8 + N_top + N_val:
  - N_top is the number of top-level `estimators` keys;
  - N_val is the number of keys in `systems/lorenz63/validation/estimators`, that is, the estimators trained before the validation snapshot (the core noise level).
  - At the DEV-0 smoke this predicts 11, with the 0.02 `weights_digest` only at the top level.
- **Optional:** add the same fact to the docstring of `assert_wu0003_7a_leaves`, so that .9 does not assume the two blocks have the same key set.

**R2 (low; test strength for a4, review item 2).** No test checks that `fitted_record` hashes the chosen-K tree.

- **Where:** `tests/unit/test_experiments.py:782`. The hand-built rules hold a single map, `regimes={2: regime_map}`, with `chosen_regimes=2`.
- **Why it matters:** a mutation that hashes another fitted K would pass the test. Examples are the first key, the largest K, or a fixed K. Production fits several K values (`config.regime_counts`), and the digest must follow `chosen_K`, the tree that A5 deploys.
- **Fix:** add a decoy map under a second K whose tree splits elsewhere, and assert that the digest still equals the hand value of the chosen stump. This needs no tolerance; the check is exact.

**Note, not counted as a finding.** `status` 0 (scipy stopped at `max_nfev`) is now recorded but not flagged.

- This changes nothing in this unit: a fit that stops at the evaluation limit was used unflagged before, and B1 item 3 asks only that the outcome be recorded.
- The owner may want .9 or the diagnostics to list `status == 0` explicitly.
