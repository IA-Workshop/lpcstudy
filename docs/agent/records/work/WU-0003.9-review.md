## Findings

**R1 (blocker): the discrete-count exception is much wider than A6's list, and top-level `handling` counts license 0.1·hw for every system.**

- **Where:** `tools/compare_runs.py:446-467` (`count_scope`), `470-478` (`in_scope`), `642`, `693` and `703-704`. The constants are at `157-162`.
- **The global licence.** For `handling/totals/<k>`, `handling/failed_variants` and any other top-level `handling` integer, `loc` returns `(None, "handling")` and `count_scope` returns `(None, "*")`. `in_scope` treats a system of `None` as matching every system and `"*"` as matching every block.
  - `handling/totals` is the sum over the systems (I checked this on P1).
  - So any per-system clip or replacement difference also changes a total. That licenses 0.1·hw on every interval leaf of every system, robustness included.
  - It also turns every one-sided leaf into "listed" instead of FAIL (`decide_one_sided`, line 642).
  - I confirmed this by calling `count_scope(("handling","totals","error_clips"),"int")`, which returns `(None,'*')`; `in_scope` is then True for `systems/rossler/H2b/...`.
  - `test_scope_is_causal_not_global` (test lines 581-596) passes only because the synthetic tree has no top-level `handling` block.
- **Every integer is treated as a count.**
  - Every integer anywhere under `systems/<s>/handling` gets whole-system scope and is itself only "listed", never failed. Examples:
    - `denominators/*`;
    - the LM `n_estimates`, `nonfinite_residuals` and `gof_dof`;
    - `lm_nonfinite_cost`, `oracle_nonfinite`, `local_dim_zero_distance`;
    - `empty_regime_fallback`, `regime_target_constant`;
    - `n_covariance_warnings`, `n_failed_resamples`, `n_excluded_nonfinite`.
  - Every integer in `H3a` and `regime_curve` (for example `n_km_not_reached`, `n_degenerate_pairs`, `pairs/[i]/[j]`) is treated as K (line 463).
  - `COUNT_SEGMENTS` adds `n_w_zero`, `n_zero_difference`, `n_screened_out` and others.
- **Why it matters.**
  - A6's exception list is K, best single, `n_states`, and clip, ν-cap and replacement counts. B1 item 3 keeps it unchanged.
  - Under OF-1 the working default explicitly refuses to widen it toward "every integer leaf of the upstream chain".
  - This is tolerance code, and its reading is looser than the plan's.
- **Fix.**
  - Map the exception to an explicit set:
    - `chosen_K` and `realized_K` for K;
    - `best_single`;
    - `n_states` and the state denominators;
    - counters whose names are clips, ν-cap clips or replacements.
  - Scope rules:
    - Give `handling/totals` and `handling/by_system` mirrors no scope of their own; their per-system source carries the scope.
    - Never let a `None` system match every system.
  - Any other differing integer is exact (FAIL). Alternatively, list it with no licence (OF-1 style), but then add it as an owner question.
  - Add tests on a small extract of the real schema (the `handling` subtree of the S3 pair): a per-system clip difference must not license another system, and a `totals` difference must license nothing by itself.

**R2 (blocker): TD passes when the two runs do not have the same systems.**

- **Where:** `compare_runs.py:844` (it intersects the systems) and `855-860`, and `run_td_only` at `1035`.
- **What happens.** If one run lacks a system, its 6 parts are neither computed nor counted as errors. I removed `chua` from P1 and got `k = 12`, `n_error = 0`, so the exit is 0 in `--td-only` mode. In full mode the missing system's leaves are "reported" (`decide_one_sided`, TD branch), so the exit is also 0.
- **Why it matters.** B1 item 5 fixes 18 parts. Dropping 6 parts silently is a PRIME.4 issue: they are printed only as "parts computed 12", while the result says PASS.
- **Fix.** Use the union of systems. Count a part missing on either side as NOT COMPUTABLE (exit 2), and print the expected count (6 × systems). Add a test with one system deleted from one run, for both full mode and `--td-only`.

**R3 (must fix): in T3 the LM rules are T2's for every kind, but A6 T3 says "network chain as T2; other chains as T1".**

- **Where:** `compare_runs.py:751-782` (`lmrow` tests only `tier.name == "T1"`) and `892-894`.
- **What happens.**
  - The LM summaries have the kinds `oracle`, `eval` and `check` (`pipeline.py:568`), plus a pooled block.
  - The `oracle` kind is not network chain. With only the weights differing (T3), it should keep the T1 rules: `fraction_no_decrease` exact, 1e-8 relative, and the per-estimate check.
  - Instead it gets the two-proportion band, NOT COMPUTED order-statistic bands, and class (c) at 1e-4.
  - The tool treats T3 exactly as T2.
- **Fix.** In T3, apply the T1 LM rules to every LM summary unless its kind is known to be network chain. Ask the mathematician for the kind-to-chain map; until then the strict default is T1 for the `oracle` and `check` kinds and for the pooled block. Add a T3 test on `lm/by_kind/oracle/fraction_no_decrease`.

**R4 (must fix): `--tol-other` loosens classes (b) to (g) beyond the O3 ceiling with no finding.**

- **Where:** `compare_runs.py:1047` and `1058`.
- **What happens.** Any positive value is accepted. With `--tol-other 1` every (b)-to-(g) exceedance passes and the RESULT line reads PASS.
- **Why it matters.** A6 says a tolerance above 1e-4 "is a finding (O3); it is not adopted silently". B1 item 4 applies O3 to both class groups.
- **Fix.** Reject values above 1e-4 with exit 2. Alternatively, accept them only with a printed O3 line and a non-zero exit, pending an owner ruling. Add a test.

**R5 (owner question to record): on T1 to T3 pairs O3 is labelled "information", not a finding.**

- **Where:** `compare_runs.py:904-906` and `1002-1004`.
- **The conflict.** B1 item 4 applies O3 to both class groups, and d3 evaluates O3 on the kernel pair, which is T2. The developer set it to "information" outside T0 because a leaf that passes at 0.5× its tolerance would always trigger O3, which conflicts with d2.
- **Why it matters.** That is a real conflict inside the plan, but it was resolved in the looser direction without an owner question.
- **Fix.** Print "O3 FINDING" on every tier. Keep the exit code as it is, and record the d2/O3 conflict in the Log as an open question for the owner or planner.

**R6 (planner or main session): the tool cannot give a usable result on the plan's own run pairs.**

- **Where:** A4. R1 runs without `--skip-robustness`; R2 and R3 run with it (`__main__.py:187`). The tool code involved is `compare_runs.py:637-645`.
- **What happens.**
  - With `--skip-robustness` the `robustness` block is absent.
  - On R1 against R2 (T0, GPU) every robustness leaf is a one-sided FAIL, so the result is exit 1.
  - On R1 against R3 (T1), the outcome of the same leaves flips to "listed" whenever a top-level handling total differs (R1).
- **Not a loosening by the tool.** The tool is right to fail one-sided leaves. But WU-0003.4 cannot use the comparison as the plan defines the runs.
- **Fix (routing).** Either run R1 to R3 with the same flags, or add an explicit block exclusion that is counted and printed (for example `--exclude-block robustness`, printed as "excluded by option" with leaf counts). Either needs a planner decision.
