## Findings

- **Where:** `tests/integration/test_states_dump.py:12-20` and `:91-142` (b3 omits clip counts); `lpcstudy/dump.py:291-292` (`handled` only for the test split).
- **Why it matters:** b3 lists "clip counts" among the leaves the dumped arrays must reproduce. The core cell's handling counts (`handling/cells/<core>/...`) pool the construction, calibration and test splits (`pipeline.cell_handling`). From the test split's `handled` alone they cannot be reproduced. This is the reason Q1 gave for dumping the LM arrays of all three splits, but it was not applied here. The b3 item is dropped silently from the test's list, and the integration run is a run-once preset, so the gap should be closed before it starts.
- **Fix:** dump `oracle_handled` and `eval_handled`, plus the per-split `clip_entries` totals, for all three splits. A natural home is `handling/<split>/`: n_s × 8 int64, negligible size. Then add a b3 assertion that their sums equal the stored cell counts, exactly. Alternatively, have the planner remove "clip counts" from b3, with the reason recorded. Either way, do it before the integration tier runs.

  - **Answer (developer, fix round 1):** fixed in the fix-round commit (see the unit Log): `handling/<split>/{oracle,eval}_handled` and `_clip_entries` for all three splits; b3 sums them and compares exactly with `handling/cells/<core>/by_kind/<kind>/counts`.

**R2 (medium; plan b4 "in every split cell" not checkable on the sweep cells).**
- **Where:** `lpcstudy/dump.py:300-315` (the sweep groups hold the halves but not the full moments); `tests/integration/test_states_dump.py:145-153` (b4 on the core cell only).
- **Why it matters:** B1 item 8 puts the split-half moments in the H2b cells, and b4 requires (m_A + m_B)/2 = m in every split cell. The sweep groups lack `E_C`, `E_P` and `C` at H_ref, so the identity cannot be checked there, and .8's D6 cannot recombine the halves against the full moment either.
- **Fix:** add `E_C`, `E_P` and `C` (full, `(nS,)`, at H_ref) to each `sweep/...` group (24·nS bytes per cell). Document them in the docstring and extend b4 to every sweep group. The schema has not been written by any run yet, so `/1` can stay.

  - **Answer (developer, fix round 1):** fixed in the fix-round commit: `E_C`, `E_P`, `C` at `H_ref` in every sweep group, and b4 runs on the core cell and every sweep cell.

**R3 (low; Q7 is a looser b4 criterion, labelled "stricter").**
- **Where:** `tests/integration/test_states_dump.py:149-153`; Log Q7.
- **Why it matters:** the plan's bound is 1e-13 times the mean absolute term. For C the test uses sqrt(E_C E_P), which is at least mean|e_C e_P| by Cauchy–Schwarz, so the smoke check of C is wider than the plan's by that ratio. It was stated before any run, so it is not an after-the-fact loosening. But it is a developer change to an acceptance criterion without the planner's sign-off.
- **Fix:** have `ensemble_moments(half_out=...)` also return the exact scale. That is `abs_cross = mean|e_C e_P|` over all draws (the same chunks, dump only), or `abs_cross_A` and `_B`. Dump it and use it in b4. Alternatively, record the planner's acceptance in the plan and correct the Log's label "stricter" for Q7.

  - **Answer (developer, fix round 1):** fixed in the fix-round commit: the exact scale is dumped (`abs_cross` from `ensemble_moments(half_out=...)`, as `core/abs_C` and `sweep/<cell>/abs_C`) and b4 uses it, the plan's scale; open question 7 is superseded.

  - **Answer (developer, fix round 1):** fixed in the fix-round commit: the text says \"H_ref, 2 and 4 LT\" and the denominator is `cp.size * len(horizons)`; the test asserts both (\"of 900\").
