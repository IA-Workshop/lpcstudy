## Answers to the four questions

1. Flags accepted by the CPU client (registered, XLA@91888df): `--xla_cpu_multi_thread_eigen` (bool, default true), `--xla_force_host_platform_device_count` (int, default 1), `--xla_cpu_parallel_codegen_split_count` (default 32; compile-time LLVM parallel codegen only, not run-time threads), `--xla_cpu_use_thunk_runtime` (deprecated). `intra_op_parallelism_threads` is not shown as a registered XLA_FLAGS entry (claim 5: strong inference, not an exact grep). The TF-style variables `TF_NUM_INTRAOP_THREADS` / `TF_NUM_INTEROP_THREADS` are not read by `DefaultThreadPoolSize` or by `port.cc` `MaxParallelism` (the port.cc reader reported none; the pjrt/utils.cc function shows only `PJRT_NPROC` and `NPROC`). So they have no effect in XLA's PjRt CPU client (inference from the code read; **unconfirmed** elsewhere in the tree).
2. What actually caps the pool for ordinary jitted float64 CPU work (per the code read): (a) `PJRT_NPROC=N` (checked first) or `NPROC=N` environment variable, read by `getenv` and not an XLA flag, so it cannot abort XLA; (b) a CPU affinity mask (`taskset -c 0-3 ...` or `os.sched_setaffinity` before importing jax), which changes `sched_getaffinity` and so `MaxParallelism`. `--xla_cpu_multi_thread_eigen=false` does not cap dots or elementwise ops in this version (it only reaches the FFT thunk in the files read). Floors: `num_threads >= xla_force_host_platform_device_count`; the pool is never below 0 and `NPROC=0` gives `max(0,0)=0` (behaviour at 0 not read; avoid 0). Pool names: XLAEigen, XLACompile, XLAExecute, XLAPjRtCpuClient. Whether the calling Python thread adds one more worker (so "N" may mean N+1 busy threads) is **unconfirmed**; measure it.
3. Documented way in jax docs: none found. The FAQ and config_options pages (docs.jax.dev) have no thread option (claims 10, 11). The only maintainer-level statements are the 2019 GitHub comments (claim 13), which are outdated. `PJRT_NPROC`/`NPROC` appears only in a source comment in `xla/pjrt/utils.cc`, and a 2024 user comment in issue #743.
4. Caveats: (i) unknown XLA_FLAGS token aborts via QFATAL (claims 1, 2), including bare words without `--`; (ii) the old 2019 recipe contains such a bare token; (iii) XLA_FLAGS is read when XLA's flags are first parsed (backend init), so set env vars before `import jax` is executed and before any backend initialisation; (iv) async dispatch: `jax_cpu_enable_async_dispatch` defaults True, so computations are launched on `XLAPjRtCpuClient` pool threads; the setting `False` runs inline for non-parallel computations only (claim 10); this does not reduce intra-op threads; (v) `NPROC`/`PJRT_NPROC` is an undocumented knob with a source comment saying it exists for Google's CI and a TODO to replace it, so it may be renamed; check on each pin change; (vi) cgroup CPU quotas are not seen (claim 7, partly inferred); (vii) OPENBLAS/MKL/OMP variables control only code linked to those libraries (numpy/scipy in the same process), still useful for the numpy side; the 2023 comments say combining them with the XLA settings was needed for low CPU usage.

## How a developer should verify (nothing was run by the researcher)

Run each in a subprocess with a time limit, one at a time, on CPU, with the pinned jax. Stop after each result.

1. Validity of an XLA_FLAGS entry (aborts at backend init, not at import): `XLA_FLAGS="--xla_cpu_multi_thread_eigen=false" python -c "import jax; jax.devices(); import jax.numpy as jnp; jnp.ones(3).block_until_ready()"`. Exit code 0 means accepted. For a bad flag expect a fatal log "Unknown flag in XLA_FLAGS: ..." and a nonzero (abort) exit status. Test the exact string the wrapper will export, including quoting. The check must execute a computation, because flag parsing happens when the backend is created.
2. Which knob caps the pool: run a fixed jitted workload (float64, e.g. a large `jnp.dot` and an elementwise `jnp.sin` loop; set `JAX_ENABLE_X64=1`) under `NPROC=1`, `PJRT_NPROC=2`, `taskset -c 0,1`, and no limit. Count threads and CPU use, for instance via `/proc/self/status` `Threads:` and the process's `/proc/<pid>/task/*/comm` (pool threads should be named XLAEigen etc., per `GetThreadOptions()` names) and the user-plus-sys CPU time divided by wall time (`resource.getrusage`). Pass criterion: CPU/wall time at most about LPC_THREADS (+1 for the Python thread). Check that `PJRT_NPROC` takes precedence over `NPROC`.
3. Confirm the jaxlib XLA commit for the wheel: `python -c "import jaxlib, jax; print(jax.__version__, jaxlib.__version__)"` and compare against the pinned commit above (jaxlib does not expose the XLA hash; the version check is only a proxy).
4. Because `NPROC` is undocumented, make the wrapper export `PJRT_NPROC` and `NPROC` as plain env variables, not XLA_FLAGS (no abort risk), and add the check from step 2 as an integration check of the wrappers.
